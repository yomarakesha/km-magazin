# POS / Касса продавца — дизайн

**Дата:** 2026-07-14 · **Ветка:** dynamic · **Статус:** утверждён к реализации

## Цель

Дать продавцу (роль `sales`) экран-кассу для продаж «с прилавка»:
сканирование штрихкода, немедленное списание проданного со склада, ввод
реальной суммы продажи (скидка/долг), печать чека A4. Долги фиксируются с
именем и телефоном должника и гасятся позже. Продажи попадают в отчёты
(выручка/прибыль) и в складской журнал.

Продажа с кассы хранится в **отдельной сущности `Sale`** (не переиспользуем
`Order`) — онлайн-заказы и офлайн-касса разделены, но обе пишут в общий
складской леджер (`StockMovement`) и в общий отчёт «Продажи» с разбивкой по
каналу.

## Роли

- Доступ к кассе и продажам: `sales` (owner проходит везде).
- `POST /void` (отмена продажи, возврат остатка): **owner-only**.
- Склад/контент к кассе не имеют доступа.

Согласовано с моделью прав «по полю» (см. `ecommerce-control-system` память):
складчик владеет остатком через приход/списание, продавец списывает через
продажу — обе операции идут через `app/stock.py::log_movement`, счётчик и
леджер меняются в одной транзакции.

## Модель данных

### Новое поле `Product.barcode`
`Mapped[str | None]`, nullable, индекс. Заводской штрихкод (EAN/UPC). Поиск на
кассе: сначала по `barcode`, затем fallback по `sku`, затем по названию.
Миграция: `ALTER TABLE shop_products ADD COLUMN barcode`.

### `Sale` (`shop_sales`)
| поле | тип | смысл |
|------|-----|-------|
| id | int PK | номер чека |
| seller | str | username продавца (кто провёл) |
| created_at | datetime (aware UTC) | момент продажи |
| subtotal | int | сумма позиций по каталогу |
| sold_total | int | за сколько реально продали (вводит продавец) |
| discount | int | subtotal − sold_total (хранится вычисленным; может быть < 0 при наценке) |
| cost_total | int | сумма cost_snapshot по позициям (для маржи) |
| status | str | `paid` \| `debt` |
| payment_method | str | `cash` \| `terminal` \| `debt` |
| debtor_name | str \| None | имя должника (обязательно при долге) |
| debtor_phone | str \| None | телефон должника (обязательно при долге) |
| settled_at | datetime \| None | когда долг погашен |

Инвариант: `status == 'debt'` ⟺ `payment_method == 'debt'` на момент создания;
после `settle` → `status='paid'`, `settled_at` заполнен, `payment_method`
остаётся `debt` (история как оплачен долг).

### `SaleItem` (`shop_sale_items`)
| поле | тип | смысл |
|------|-----|-------|
| id | int PK | |
| sale_id | int FK→shop_sales CASCADE | |
| product_id | int FK→shop_products SET NULL | сохраняем историю при удалении товара |
| title_snapshot | str | название на момент продажи |
| price_snapshot | int | цена каталога на момент |
| cost_snapshot | int \| None | себестоимость на момент (для маржи) |
| qty | int | количество |

`subtotal = Σ price_snapshot·qty`. Цена продажи — на уровне чека (`sold_total`),
строки хранят каталожную цену. Скидка распределяется на чек, не на строку.

### `StockMovement.sale_id`
Новая FK (SET NULL) — привязка списания к продаже, зеркало существующего
`order_id`. Миграция: `ALTER TABLE shop_stock_movements ADD COLUMN sale_id`.

## API — `backend/app/routers/admin_pos.py` (prefix `/api/admin/pos`)

Роутер-зависимость: `require_role("sales")`.

### `GET /lookup?code=…`
Поиск товара для сканера. Порядок: `barcode == code` → `sku == code` →
`title ILIKE %code%` (первый). Ответ: `{id, title, price, currency, stock_qty,
barcode, sku}` или 404 если ничего.

### `POST /sales`
Тело (`SaleIn`):
```
items: [{product_id: int, qty: int (>=1)}]   # min_length 1
sold_total: int | None                        # None → = subtotal
payment_method: "cash" | "terminal" | "debt"
debtor_name: str | None
debtor_phone: str | None
```
Валидатор (mode="after"): если `payment_method == "debt"` → `debtor_name` и
`debtor_phone` обязательны и непусты, иначе 422.

Логика (одна транзакция):
1. Для каждой позиции загрузить `Product`, собрать `price_snapshot`,
   `cost_snapshot`, `title_snapshot`.
2. Списание остатка **атомарно** для tracked (`stock_qty IS NOT NULL`):
   guarded `UPDATE … WHERE stock_qty >= qty` (как в create_order). Если
   `rowcount == 0` для tracked-товара → 409 «недостаточно на складе: {title}».
   Untracked (`stock_qty IS NULL`) продаётся без списания.
3. `log_movement(kind="sale", qty_delta=-qty, sale_id=…, username=seller)` для
   каждой tracked-позиции (после flush, как требует stock.py).
4. Создать `Sale` + `SaleItem`. `subtotal = Σ`; `sold_total` = вход или subtotal;
   `discount = subtotal - sold_total`; `cost_total = Σ cost_snapshot·qty`;
   `status/payment_method` из тела.
5. Инвалидация SSR-кеша магазина (остаток влияет на витрину) — как у warehouse
   роутера через middleware.
6. Ответ: сериализованный `Sale` + позиции (данные для чека).

### `GET /sales?date_from=&date_to=&debt=`
История POS-продаж, свежие сверху. `debt=true` → только `status='debt'`.

### `GET /sales/{id}`
Детали продажи (для чека и карточки).

### `POST /sales/{id}/settle`
Погасить долг: только если `status='debt'` (иначе 409). → `status='paid'`,
`settled_at=now`. Роль `sales`.

### `POST /sales/{id}/void` — **owner-only** (`require_role()`)
Отмена продажи: вернуть остаток для tracked-позиций (`kind='return'`,
guarded UPDATE +qty, sale_id), пометить продажу отменённой. Реализация v1:
удаляем `Sale` после возврата остатка (леджер хранит след через sale_id=NULL
после SET NULL + note). Возврат идемпотентен по позициям.

## Интерфейс

### `/admin/pos` — касса
- Поле **Штрихкод** (autofocus, `onKeyDown Enter` → lookup → добавить в чек;
  повторный скан того же товара → qty+1). Сканер работает как клавиатура.
- Список позиций: название · цена каталога · `[− qty +]` · сумма строки ·
  удалить. Пусто → подсказка «отсканируйте товар».
- Панель итога (sticky снизу/сбоку):
  - Подытог (авто)
  - **Продано за** — числовое поле, по умолчанию = подытог; показывает
    скидку/наценку разницей.
  - Оплата: сегмент `Наличные | Терминал | Долг`.
  - Если **Долг** → поля Имя должника + Телефон (маска через `lib/phone.ts`).
  - Кнопка **Провести и печать** (disabled пока чек пуст; при долге — пока
    имя/телефон пусты).
- После проведения: открыть чек в печать (`window.print`) и очистить кассу,
  вернуть фокус на штрихкод.

### `/admin/pos/sales` — продажи и долги
- Таблица продаж: №, дата, продавец, итог, статус (оплачено/долг), канал оплаты.
- Фильтры: период, переключатель **Только долги**.
- Строка долга: кнопка **Погасить** + сумма долга подсвечена.
- Действия: **Чек** (перепечать), **Отмена** (void, видна только owner).

### Чек A4 — `/admin/pos/receipt/[id]`
Печатная страница, `@media print` (скрыть админ-хром). Содержит: шапка магазина
(название, телефон, адрес из `ShopSettings`), № чека и дата, продавец, таблица
позиций (название, кол-во, цена, сумма), Подытог, Скидка (если есть), **ИТОГ**,
способ оплаты; если долг — блок «В долг: {имя}, {телефон}»; строка для подписи.
Кнопка «Печать» (не печатается сама).

### Навигация
Пункт **«Касса»** (`/admin/pos`) в `app/admin/layout.tsx`, `roles: ["sales"]`.
Опционально «Продажи/Долги» отдельным пунктом или вкладкой внутри кассы —
делаем отдельным пунктом `/admin/pos/sales`, `roles: ["sales"]`.

## Отчёты

Отчёт **«Продажи и прибыль»** (`admin_reports.py::/sales`) расширяется: выручка,
COGS и прибыль считаются по **онлайн-заказам + POS-продажам** за период с
разбивкой по каналу (`online` / `pos`). Добавляется KPI **«Долги»** — сумма
непогашенных (`Sale.status='debt'`) `sold_total`. CSV-выгрузка сохраняет
разбивку. Складской отчёт не меняется — POS-списания уже видны как `kind='sale'`
в журнале.

## Обработка ошибок / край

- Долг без имени/телефона → **422** (валидатор схемы).
- Недостаток остатка (tracked) → **409** с названием товара, транзакция
  откатывается целиком (ни списания, ни продажи).
- `sold_total > subtotal` (наценка) — разрешено, `discount` отрицательный.
- `sold_total < 0` или qty < 1 → 422.
- Товар не найден по коду → 404 (касса показывает «не найдено»).
- Погашение уже оплаченной продажи → 409.
- Void не-owner → 403.
- Конкурентные продажи одного товара — атомарный guarded UPDATE, второй
  получает 409 при нехватке.

## Тестирование (pytest, `tests/test_pos.py`)

- продажа списывает остаток и пишет `StockMovement kind='sale'` с `sale_id`;
- `subtotal`/`sold_total`/`discount`/`cost_total` считаются верно;
- продажа в долг без имени → 422; с именем → создаётся `status='debt'`;
- недостаток остатка tracked → 409, остаток не тронут;
- untracked (`stock_qty=None`) продаётся, леджер не пишется;
- `settle` гасит долг (status→paid, settled_at), повтор → 409;
- `void` (owner) возвращает остаток, не-owner → 403;
- `lookup` находит по barcode, по sku, по названию.

Тесты используют дельта-подход (общая тестовая БД, см. существующие
report-тесты) — сравнивать приращения, не абсолютные суммы.
